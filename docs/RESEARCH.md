# Detect strings, warp only where rays land

A "mudworm spot" is a **Floor Drop**: a one-click reward spot on a grass block in Galatea's Moonglade Marsh, also found in Torrhus Canyon and the Critter Safari. Each click rolls either one Mudworm Shard (about a third of the time) or a stack of Fig or Mangrove Logs ([Floor Drops wiki](https://hypixelskyblock.minecraft.wiki/w/Floor_Drops)). On the client a spot shows as a `minecraft:happy_villager` particle about one block above the grass plus **exactly three `ItemDisplay` entities holding string** inside that block. Skyblocker requires both signals ([Skyblocker FloorDrops.java](https://github.com/SkyblockerMod/Skyblocker/blob/master/src/main/java/de/hysky/skyblocker/skyblock/hunting/FloorDrops.java)). The server only sends particles and entities near the player, so "find every spot on the island" means patrolling and remembering candidates, not scanning once from one place. Etherwarp never goes through walls by design: the server targets the first etherwarp-solid block on the look ray, and the warp works only if the two cells above that block are free ([Odin Etherwarp.kt](https://github.com/odtheking/Odin/blob/b412ad1c2146a87832e4a589d35329022783e535/src/main/kotlin/com/odtheking/odin/features/impl/render/Etherwarp.kt)). So the macro should never pick a block and hope the aim reaches it. It should run a voxel-exact DDA from the sneaking eye (1.27 on Galatea) and accept only hops where that ray's first hit is the planned block, with clear headroom and some margin. Use one A* over standing cells with walking edges and lazily generated etherwarp edges, plus a nearest-neighbour/2-opt tour that is re-planned as spots appear and disappear. Click with a right-click from an item that has no right-click ability (not the AOTV), and confirm success with the `FLOOR DROP!` chat line and the string displays disappearing. Two caveats apply throughout. Hypixel prohibits this kind of automation and bans for it. And several key numbers (respawn rate, server view range, Hypixel's exact ray rules) are unpublished and have to be measured in-game.

## A Floor Drop is three strings and a sparkle

The game's name for the mechanic is "Floor Drop"; "Mudworm" is the shard it can give. Floor Drops "appear on grass blocks around the Moonglade Marsh", were added on 2025-06-05, later spread to Torrhus Canyon and the Critter Safari, and Foraging Fortune and Hunter Fortune boost their yield ([Floor Drops wiki](https://hypixelskyblock.minecraft.wiki/w/Floor_Drops)). A forum guide describes them as "strings popping out of the ground", which matches what the client receives ([hypixel.net guide](https://hypixel.net/threads/getting-30-attributes-to-unlock-advanced-view-no-bazaar.5938088/)). A shard result posts the chat line `FLOOR DROP! You found <name> Shard on the ground!`, regex `inventory.attributeshards.floor-drop.shard` ([SkyHanni-REPO regexesModern.json](https://github.com/hannibal002/SkyHanni-REPO/blob/main/constants/regexesModern.json); [NoFrills ShardTracker.java](https://github.com/WhatYouThing/NoFrills/blob/main/src/main/java/nofrills/features/hunting/ShardTracker.java)). The log-result line is probably the same with `x<count>`, but no source confirms it.

Skyblocker's implementation is the reference detector. It listens to `ClientboundLevelParticlesPacket` and keeps only `ParticleTypes.HAPPY_VILLAGER`. It takes `BlockPos.containing(x, y - 1, z)` as the spot block and accepts it only if **three `Display.ItemDisplay` entities whose item is `Items.STRING`** sit in a 1×1×1 box on that block. It re-confirms every 2 s, drops a spot after 5 s without confirmation, runs only in the Marsh, Torrhus Canyon and Safari, and clears on server join ([Skyblocker FloorDrops.java](https://github.com/SkyblockerMod/Skyblocker/blob/master/src/main/java/de/hysky/skyblocker/skyblock/hunting/FloorDrops.java)). The original PR dropped line-of-sight raytracing for detection because it was unreliable ([Skyblocker PR #1325](https://github.com/SkyblockerMod/Skyblocker/pull/1325)). The string displays are the stronger signal, because happy_villager particles have other sources. A macro can go further than Skyblocker: scan all loaded `ItemDisplay` entities in `ClientLevel`, group them by block, and treat any block with three strings as a candidate without waiting for a particle. Their disappearance is then the natural "spot consumed" signal. That design is an inference from the Skyblocker code, not something a mod already ships.

The drop table matters only for the profit tracker. One wiki summary gives **33.02% for one Mudworm Shard** and the rest split between 50/100 Fig Logs and 40/80 Mangrove Logs. A second summary of the same page lists different amounts, adds Invisibug Shards, and marks the odds "More Info Needed", so treat the odds as unconfirmed ([Floor Drop wiki](https://hypixelskyblock.minecraft.wiki/w/Floor_Drop)). The shard's Bazaar id is `SHARD_MUDWORM` ([NEU-REPO attribute_shards.json](https://github.com/NotEnoughUpdates/NotEnoughUpdates-REPO/blob/master/constants/attribute_shards.json)), and one 24 h Coflnet window (capture date unknown) priced it around **54k–74k coins** ([Coflnet](https://sky.coflnet.com/item/SHARD_MUDWORM)). No source gives the respawn interval, how many spots exist at once, or whether spots are per-player. Spots per hour, and so coins per hour, are therefore unknown.

### Click with a free hand, never the AOTV

No primary source says which click consumes a spot. Skyblocker removes a spot on **either** `AttackBlockCallback` (left-click) or `UseBlockCallback` (right-click) ([Skyblocker FloorDrops.java](https://github.com/SkyblockerMod/Skyblocker/blob/master/src/main/java/de/hysky/skyblocker/skyblock/hunting/FloorDrops.java)), and the PR that added it has a commit titled "Remove waypoint if block is right clicked" ([Skyblocker PR #1325](https://github.com/SkyblockerMod/Skyblocker/pull/1325)). No source mentions a minigame, a channel time or a required tool. The recommended action is one `mc.gameMode.useItemOn(p, MAIN_HAND, hit)` on the grass block's top face, holding an item with no right-click ability (or an empty slot). If no `FLOOR DROP!` line arrives within about 1 s, fall back to `startDestroyBlock(pos, dir)` plus `swing`. Both method names are confirmed for 26.1.2 by Fabric API's own mixins and the user's code ([FAPI MultiPlayerGameModeMixin.java](https://github.com/FabricMC/fabric/blob/0.145.4+26.1.2/fabric-events-interaction-v0/src/client/java/net/fabricmc/fabric/mixin/event/interaction/client/MultiPlayerGameModeMixin.java); [HM MudwormMacro.java](file:///home/user/Hunting-macro/src/main/java/com/nablzz/addons/mudworm/MudwormMacro.java)). The user's reference code defaults to clicking **with the Aspect of the Void, action 0 (right-click block)**. That is the riskiest choice available: a right-click without sneak fires Instant Transmission and is likely to teleport the player off the spot ([Aspect of the Void wiki](https://hypixelskyblock.minecraft.wiki/w/Aspect_of_the_Void)). Swap to a neutral slot before clicking. One more detail: a short-grass plant on top of the grass block has an outline shape, so an `OUTLINE` clip from the crosshair hits the plant before the block. Aim so the real crosshair ray hits the grass block's face, rather than only building a synthetic `BlockHitResult`. The synthetic hit result would be accepted by the client, but how the server checks look direction is unknown.

## Spots are only visible inside the server's tracking bubble

"Every spot on the island" is limited by what the server sends. In vanilla, particle packets reach players within 32 blocks unless the long-distance flag is set (then 512). Display entities exist on the client only while the server tracks them, at most about 10 chunks and capped by server view distance. These are vanilla defaults; Hypixel's actual values for Galatea are unverified. The workable approach is a **patrol plus memory** model. Index loaded chunks with Fabric's `ClientChunkEvents.CHUNK_LOAD/CHUNK_UNLOAD` (`(ClientLevel, LevelChunk)`, verified at tag 0.145.4+26.1.2) ([FAPI ClientChunkEvents.java](https://github.com/FabricMC/fabric/blob/0.145.4+26.1.2/fabric-lifecycle-events-v1/src/client/java/net/fabricmc/fabric/api/client/event/lifecycle/v1/ClientChunkEvents.java)). Seed the index at start by looping `level.getChunk(cx, cz, ChunkStatus.FULL, false)` over `options.getEffectiveRenderDistance()`, the same no-mixin method Fabric's gametest uses ([FAPI TestClientLevelContextImpl.java](https://github.com/FabricMC/fabric/blob/0.145.4+26.1.2/fabric-client-gametest-api-v1/src/client/java/net/fabricmc/fabric/impl/client/gametest/context/TestClientLevelContextImpl.java)). Then scan sections on the client thread with a time budget, skipping `hasOnlyAir()` sections as Odin does ([Odin WorldScan.kt](https://github.com/odtheking/Odin/blob/main/src/main/kotlin/com/odtheking/odin/features/impl/dungeon/map/WorldScan.kt)). That scan builds the terrain model (standable cells, landable etherwarp tops) that the pathfinder needs, while the string-display scan finds the spots themselves.

The Marsh's extent comes from SkyHanni's island graph: its 16 "Moonglade Marsh" nodes span roughly **x −708…−603, y 92…115, z −46…77**. The Galatea graph has no `floor_drops` tags. The Safari graph, by contrast, has about **110 fixed `floor_drops` nodes**, used by SkyHanni's `/shnavigateall Floor Drops` ([SkyHanni-REPO GALATEA.json](https://github.com/hannibal002/SkyHanni-REPO/blob/main/constants/island_graphs/GALATEA.json); [SAFARI.json](https://github.com/hannibal002/SkyHanni-REPO/blob/main/constants/island_graphs/SAFARI.json)). That points to Floor Drops spawning from fixed candidate sites, not random grass. If the Marsh works the same way, the macro should **learn candidate sites** (persisting every confirmed spot block) and build its patrol from them. Over sessions, that turns a blind sweep into a short loop over known sites. No mod repo publishes Marsh coordinates, so this list has to be built in-game.

On the particle path, the user's mixin injects into `ClientPacketListener.handleParticleEvent` at `HEAD` ([HM ClientPacketListenerMixin.java](file:///home/user/Hunting-macro/src/main/java/com/nablzz/addons/mushroom/mixin/ClientPacketListenerMixin.java)). Because `PacketUtils.ensureRunningOnSameThread` re-runs the handler on the main thread, a HEAD hook most likely fires twice per packet, once on the netty thread. Inject at `RETURN` as Skyblocker does, or after the `ensureRunningOnSameThread` call as Fabric's command mixin does ([SB ClientPacketListenerMixin.java](https://github.com/SkyblockerMod/Skyblocker/blob/main/src/main/java/de/hysky/skyblocker/mixins/ClientPacketListenerMixin.java); [FAPI command mixin](https://github.com/FabricMC/fabric/blob/0.145.4+26.1.2/fabric-command-api-v2/src/client/java/net/fabricmc/fabric/mixin/command/client/ClientPacketListenerMixin.java)). Three more fixes from the comparison with Skyblocker: add the three-string confirmation, which the current tracker lacks; resolve the spot as exactly `y − 1` instead of scanning down 0–3 blocks; and stop treating remembered far spots as live, because they cannot be confirmed outside tracking range.

## Etherwarp's first-hit rule makes "through walls" structurally impossible

Ether Transmission (Etherwarp Merger or Conduit on an AOTE/AOTV) is **sneak + right-click** and costs **180 mana and 1 Soulflow** before reductions. The base range is **57 blocks plus 1 per Transmission Tuner, maximum 61** ([Etherwarp Conduit wiki](https://hypixelskyblock.minecraft.wiki/w/Etherwarp_Conduit); [Aspect of the Void wiki](https://wiki.hypixel.net/Aspect_Of_The_Void)). Every mod reads range as `57 + tuned_transmission` from the item's custom data, gated on `ethermerge == 1` ([Skyblocker TeleportOverlay.java](https://github.com/SkyblockerMod/Skyblocker/blob/ca1163e2b7309113cc4dd3c084829d4417606235/src/main/java/de/hysky/skyblocker/skyblock/teleport/TeleportOverlay.java)). Read that value instead of hard-coding it, and read mana cost from lore, since Ultimate Wise changes it.

The server casts a ray from the player's eye along the look vector. The **first etherwarp-solid block** it meets is the target, and the warp succeeds only if the two cells above are free ([Etherwarp Conduit wiki](https://hypixelskyblock.minecraft.wiki/w/Etherwarp_Conduit)). A wall between you and the intended block is simply the first hit, so the warp either lands on the wall top (if it has headroom) or fails. The real risk is not tunnelling but **mis-prediction**: the client thinks the ray reaches block B, while the server's ray clips a corner, a sign or a leaf first. Hypixel's block rules are not public. The mods have reverse-engineered them, and they disagree at the edges:

| Model | Ray passes through | Stops the ray | Headroom test |
|---|---|---|---|
| Odin (most detailed) | Empty collision, plus buttons, skulls, ladders, flower pots, levers, nether wart, repeaters/comparators, redstone torches, piston heads, bubble columns | Everything else, including signs, banners, tripwire hooks, pressure plates | Feet cell `y + max(1, ceil(collisionMaxY))` and the cell above must not obstruct; skulls, pots, ladders, repeaters and comparators obstruct feet |
| Firmament | Empty collision, plus skulls, repeaters/comparators, dripleaf stem, carpets, cocoa, ladders, sea pickles, flower pots | Signs, hanging signs, banners | `above()` and `above(2)` transparent; also fails if the crosshair's vanilla hit is an interactable block (chest, door, trapdoor, gate, hopper...) |
| NoFrills | Empty collision, plus heads, cocoa, flower pots, ladders; fluids ignored | Signs, snow layers, pressure plates, banners | Per-block offset table; fences/walls shift the target up one |
| Skyblocker (strictest headroom) | Air, empty collision, carpets, flower pots, cobwebs, snow ≤3 layers | Everything else | `above()` and `above(2)` must be literal air |

Sources: [Odin Etherwarp.kt](https://github.com/odtheking/Odin/blob/b412ad1c2146a87832e4a589d35329022783e535/src/main/kotlin/com/odtheking/odin/features/impl/render/Etherwarp.kt), [Firmament EtherwarpOverlay.kt](https://github.com/nea89o/Firmament/blob/4d1ed0013927328d91892252b596c0f66ceb5d10/src/main/kotlin/features/items/EtherwarpOverlay.kt), [NoFrills EtherwarpRaycastContext.java](https://github.com/WhatYouThing/NoFrills/blob/74e9317c1a7b8484a575b2f177479f5e3f2bfb9a/src/main/java/nofrills/misc/EtherwarpRaycastContext.java), [Skyblocker PredictiveSmoothAOTE.java](https://github.com/SkyblockerMod/Skyblocker/blob/ca1163e2b7309113cc4dd3c084829d4417606235/src/main/java/de/hysky/skyblocker/skyblock/teleport/PredictiveSmoothAOTE.java).

For a macro that must never fire a doomed warp, a target has to be **valid under every model at once**. That means a full solid cube (`isCollisionShapeFullBlock`), not interactable, not a carpet, slab, snow layer, fence or wall (the models disagree on these), with air above (plants with no collision at most) in both cells. Galatea's **mud** has collision height 14/16; Skyblocker special-cases it as a floor and Odin's stand offset still resolves it to y+1, so mud tops are acceptable targets ([Skyblocker PredictiveSmoothAOTE.java](https://github.com/SkyblockerMod/Skyblocker/blob/ca1163e2b7309113cc4dd3c084829d4417606235/src/main/java/de/hysky/skyblocker/skyblock/teleport/PredictiveSmoothAOTE.java)). Leaves have full collision and count as solid in every model. That matters in a mangrove marsh: canopy blocks both stop rays and are landable, and the strict-intersection rule filters them out by headroom.

### Simulate the server's ray, not the camera's

Ray geometry has three parts. First, **origin**: Galatea is modern-version-only ([Changelog 2025 June 5](https://hypixelskyblock.minecraft.wiki/w/Changelog/2025/June_5)), so use the modern **sneaking eye height of 1.27**, not the legacy 1.54 or the standing 1.62. NoFrills' "Eye Height Fix" exists precisely because legacy islands differ ([NoFrills CameraMixin.java](https://github.com/WhatYouThing/NoFrills/blob/74e9317c1a7b8484a575b2f177479f5e3f2bfb9a/src/main/java/nofrills/mixin/CameraMixin.java)). Cast from the **last position and sneak state sent to the server**, as Odin's "Use Server Position" option does with `xLast/yLast/zLast` and `lastSentInput.shift()`; those field names are unverified for 26.1.2. The user's planner uses 1.62 in places, which is wrong for etherwarp. Second, **traversal**: use an exact Amanatides–Woo DDA (Odin's `traverseVoxels`, or vanilla `BlockGetter.traverseBlocks` as Firmament uses) over a precomputed per-`BlockState` flag table indexed by `Block.getId(state)`. Skyblocker's 1-block fixed-step march can skip corners. Third, **margin**: Hypixel's exact stepping is unknown. Cast a small fan of jittered rays (a few tenths of a degree in yaw and pitch) and accept a hop only if every ray lands on the same block with valid headroom. Also reject any distance above `R − 1`. These margins are inferences; no source has tested them against the server.

The click sequence follows from that: select the AOTV, press `keyShift`, wait until `p.isShiftKeyDown()` and `Pose.CROUCHING` **plus one more tick** so the server has the sneak input, rotate (the rotation goes out in the next move packet), re-run the DDA from the actual eye along `p.getLookAngle()`, then call `useItem(MAIN_HAND)` once. Confirm with the `ClientboundPlayerPositionPacket` and/or the success sound `ENDER_DRAGON_HURT` at pitch 0.53968257, which Odin and NoFrills hook. Then check that the feet block equals `target + standOffset`, and only then plan the next hop ([Odin Etherwarp.kt](https://github.com/odtheking/Odin/blob/b412ad1c2146a87832e4a589d35329022783e535/src/main/kotlin/com/odtheking/odin/features/impl/render/Etherwarp.kt)). Hypixel snaps you to the block centre `(x+0.5, top, z+0.5)` and keeps yaw and pitch. If nothing arrives within ping + ~250 ms, re-raycast instead of re-clicking. "There are blocks in the way!" is the *non-sneak* Instant Transmission message ([Skyblocker AoteFilter.java](https://github.com/SkyblockerMod/Skyblocker/blob/ca1163e2b7309113cc4dd3c084829d4417606235/src/main/java/de/hysky/skyblocker/skyblock/chat/filters/AoteFilter.java)). If it appears, the sneak never reached the server, which is a bug signal, not a terrain one. No source documents an etherwarp cooldown; mana, Soulflow and round-trip latency set the pace.

## One A* with lazy etherwarp edges beats a ray fan from the start

The user's Nav4 planner already has walk, jump, fall, gap and ETHER node kinds. But it generates teleport candidates only **from the start node**, using a pitch −60..50° / yaw ≥5° ray fan with `level.clip` COLLIDER, a top-150 filter and a 30,000-expansion cap ([HM Nav4.java](file:///home/user/Hunting-macro/src/main/java/com/nablzz/addons/mudworm/Nav4.java)). The COLLIDER clip uses vanilla collision, not the etherwarp rules above, so it lets carpets, signs and skull-topped blocks through and is the most likely source of "warped into a wall" failures. Starting ether edges only at the origin also prevents chaining walk → warp → walk → warp.

The better design is one weighted A* over standing cells, with costs in ticks so walking and warping compare directly. **Walk edges** use Baritone's action set and cost constants: walking 4.633 ticks/block, sprinting 3.564, jump penalty 2, max fall 3 ([Baritone ActionCosts.java](https://github.com/cabaletta/baritone/blob/1.21.4/src/api/java/baritone/api/pathing/movement/ActionCosts.java); [Settings.java](https://github.com/cabaletta/baritone/blob/1.21.4/src/api/java/baritone/api/Settings.java)). Scale them by SkyBlock speed (`1 / (speed × 0.0216)` ticks per block, about 0.9 blocks/tick at speed 400, per the user's GM spec ([GM PATHFINDING_PROMPT.md](file:///home/user/glowing-mushroom-/PATHFINDING_PROMPT.md))). Forbid diagonals unless both corner cells are clear, and treat hazards as impassable. **Etherwarp edges** go from a standing cell to a landable top within R, are valid only if the jittered DDA from `(x+0.5, feetY+1.27, z+0.5)` first enters that block, and cost a constant: sneak (2–3 ticks) + aim settle (4–8) + round-trip (ping/50) + re-orient (2–4). That is about **12–20 ticks** plus a small distance tie-break and a mana penalty, with hops under ~5 blocks skipped. At speed 400 this makes walking win below roughly 15–20 blocks and saves warps for long or vertical hops such as out of the Murkwater basins (y 50–73) up to the Marsh (y 92–115). These constants are estimates; calibrate them from the macro's own etherwarp timing logs.

The cost driver is the number of candidates: tens of thousands of landable tops are within 61 blocks of any node. Generate ether edges **lazily**. Pull the 24–48 landables from the precomputed landable index with the best heuristic toward the goal, add a few random ones from a coarse 8×8×8 grid, always include the goal's own stand cells, run the DDA only on those, and memoise `(fromCell, toBlock) → visible` for the planning session. Cap at about 200 DDA tests and 100k–150k expansions per plan, with Baritone-style timeouts (500 ms primary, 2000 ms failure) and best-partial fallback. With teleports, the Euclidean walk heuristic is inadmissible. Use `h = d × min(tpb, C_ether / R)` with weight 1.5–2. Snapshot the walk grid and landable index into primitive arrays so the search can run off-thread without touching `level` ([Baritone AbstractNodeCostSearch.java](https://github.com/cabaletta/baritone/blob/1.21.4/src/main/java/baritone/pathing/calc/AbstractNodeCostSearch.java)).

Visiting all spots is a dynamic travelling-salesman problem over a changing set. Build an O(n²) estimated-cost matrix, a nearest-neighbour tour and 2-opt improvement, all in milliseconds for n ≤ 100. Run real A* only for the next one or two legs, re-plan when a spot appears or disappears, and give the current target a ~1.3× hysteresis bonus so the route doesn't flip-flop. Merge spots within interaction reach (~4.5 blocks) into a single stop. After every teleport, re-plan from the confirmed landing position instead of trusting the rest of the old path. When the live set is empty, the tour falls back to the learned candidate-site patrol.

## Port carefully to 26.1.2 and accept the ban risk

26.1 is Minecraft's first unobfuscated release. Use the `net.fabricmc.fabric-loom` plugin with plain `implementation`, Java 25, and Mojang-named Fabric APIs: `KeyMappingHelper`, `ClientCommands`, `LevelRenderEvents`, `HudElementRegistry` with `GuiGraphicsExtractor` ([Fabric 26.1 blog](https://github.com/FabricMC/fabricmc.net/blob/main/_posts/2026-03-14-261.md); [Fabric docs porting table](https://github.com/FabricMC/fabric-docs/blob/main/versions/26.1.2/develop/porting/fabric-api.md)). Skyblocker and Odin target 26.2 and 26.3, where `MultiBufferSource` and `mc.screen` are gone. Port their *logic* (detection, DDA, flag tables), not their rendering code. Several members this design depends on are **unverified for 26.1.2** because the jar could not be inspected: `LevelChunkSection.maybeHas`, `getSectionYFromSectionIndex`, `xLast/lastSentInput`, and the crouching eye constant. Confirm them with `javap` in CI before relying on them.

The rules leave no grey area. Lunar Client lists "Macros & Automated Processes" as disallowed on Hypixel ([Lunar Client](https://www.lunarclient.com/news/is-lunar-client-an-approved-mod-on-hypixel-network)), and Hypixel's own Allowed Modifications article is the authority ([Hypixel Support](https://support.hypixel.net/hc/en-us/articles/6472550754962/)). Skyblocker's highlighter is tolerated because the player still acts; auto-path plus auto-click is what crosses the line. Every etherwarp mod reviewed only *renders* predictions on Hypixel, and Odin sends simulated warps only in singleplayer ([Odin Etherwarp.kt](https://github.com/odtheking/Odin/blob/b412ad1c2146a87832e4a589d35329022783e535/src/main/kotlin/com/odtheking/odin/features/impl/render/Etherwarp.kt)). No Floor-Drop-specific detection is documented. Same-tick rotate-and-click and back-to-back warps sent before the server confirms are both bot-like patterns and the most common cause of failed warps.

## Conclusion

The research changes where the problem lies. Finding spots is mostly solved: three string displays on a grass block are an unambiguous, cheap, entity-level signal, and Skyblocker already proves the method. The open problem is coverage, not detection, because the server shows spots only nearby and the respawn rate is unknown. So the highest-value piece of work is not a better scanner but a **persistent learned candidate-site map** and a patrol over it, which the Safari's ~110 fixed sites suggest the Marsh also has. Likewise, "never etherwarp through walls" is not a constraint to add to the planner; it is guaranteed by the server's first-hit rule. What the macro must prevent is *disagreement* between its ray and Hypixel's. That pushes the design toward a strict intersection of the four mods' block rules, the correct 1.27 eye, server-side position, and jittered multi-ray confirmation, and away from vanilla `ClipContext` and ray fans.

Before any tuning, three in-game measurements decide most of the remaining parameters: the actual particle and display tracking range on Galatea, the spot respawn interval per lobby, and whether a right-click with an empty hand consumes a spot. The first two decide whether patrolling or sitting near a cluster is the better strategy. The third decides the click code. All three are cheap to log with the instrumentation the user's code already has.
